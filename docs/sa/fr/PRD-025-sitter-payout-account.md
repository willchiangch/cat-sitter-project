## 1. 背景與目的

線下轉帳需要飼主知道匯到哪個帳戶。保母在「我的」設定自己的收款帳號；每筆 CHARGE payment 建立時快照這組帳號（baseline §3.3、CQ-23），飼主付款頁只顯示快照（PRD-007）。本卡只處理帳號本身的設定、權限、保護；自 PRD-007 拆出，因為帳號資料歸 SD-SUPPLY、快照與付款歸 SD-ORDER（doc-conventions：子流程分屬不同模組時拆 PRD）。

## 2. 使用者故事

- **US-1** 身為保母，我希望設定與修改我的收款帳號，以便飼主匯款到正確帳戶。
- **US-2** 身為保母，我希望修改帳號時只影響之後的新款項，且帳號被設定或改動時我一定會收到通知，以便發現被盜改。

## 3. 角色與權限

| 動作 | OWNER | SITTER | ADMIN | 匿名 | 方案限制 |
|------|-------|--------|-------|------|---------|
| 檢視自己的收款帳號 | ✗ 403 `ROLE_MISMATCH` | 本人（保母 profile 不存在 → 404 `NOT_FOUND`） | ✗ 403 `ROLE_MISMATCH`（即時帳號不開放；可讀訂單範圍內唯讀 payment 快照，baseline §1.2、CQ-66，畫面在 PRD-007） | ✗ 401 | 無 |
| 設定 / 修改自己的收款帳號 | ✗ 403 `ROLE_MISMATCH` | 本人（保母 profile 不存在 → 404 `NOT_FOUND`） | ✗ 403 `ROLE_MISMATCH` | ✗ 401 | 無；FREE / BASIC / PRO / ULTIMATE 皆可；訂閱鎖定 / 停權不擋（BR-5） |
| 讀取他人的收款帳號 | ✗ | ✗ | ✗ | ✗ | — |
| 刪除收款帳號 | ✗ 405 | ✗ 405 | ✗ 405 | ✗ 405 | —（無此端點，BR-6） |

- 端點以 token 身分定位「自己的」帳號，不接受 sitter ID 參數；因此不存在讀他人帳號的路徑（§1.2）。
- token 為 SITTER 但該使用者的保母 profile 不存在 → 404 `NOT_FOUND`，**不自動建立** profile（審查第 1 輪 #8）。
- 錯誤判斷順序依 baseline §3.7（CQ-70）：401 `UNAUTHENTICATED` → 403 `ROLE_MISMATCH` → 404 `NOT_FOUND`（無保母 profile）→ 400 `VALIDATION_FAILED`。405 `METHOD_NOT_ALLOWED` 由路由層判定，先於以上全部。

## 4. 主流程

### 4.1 讀取、設定 / 修改

1. 保母進入「我的 > 收款帳號」，前端呼叫 GET：
   - 未設定 → 200 `{ "configured": false }`（不是錯誤狀態），畫面顯示「尚未設定收款帳號」與設定表單。
   - 已設定 → 200 `{ "configured": true, "bankCode", "branch", "accountNumber", "accountName", "updatedAt" }`，畫面顯示目前值與修改表單。
2. 填寫銀行代碼（3 位數字）、分行（1–30 字）、帳號（10–16 位數字）、戶名（1–50 字），四欄皆必填，以 PUT 整筆送出（BR-1）。
3. 前端與後端皆先正規化再驗證：帳號移除所有空白與「-」；分行、戶名去除前後空白（含全形空白，定義見 SD-GLOBAL-SPEC）；儲存正規化後的值（BR-1）。
4. 系統驗證欄位 → 比對正規化後的四欄與目前值：
   - **首次設定**（由無到有）：加密存放 → 寫稽核紀錄（變更前為空）→ `enqueue` 通知保母本人「收款帳號已設定」（BR-8、BR-11）。
   - **修改且四欄任一不同**：加密存放 → 寫稽核紀錄 → `enqueue` 通知保母本人「收款帳號已變更」（BR-8）。
   - **四欄皆相同**：不寫稽核、不發通知，回 200。
   - 稽核與通知呈現：變動的欄位名稱；變更前後的「銀行代碼 + 帳號後五碼」；不含完整帳號與戶名（BR-8、CQ-5）。
   - 通知為不可關閉類別，站內 + Email 一律排入，不受 PRD-014 偏好影響（BR-8、CQ-7）。
5. 之後建立的 CHARGE payment 快照新帳號；既有 `UNPAID` / `SUBMITTED` payment 的快照不變（CQ-23，顯示見 PRD-007 AC-1.1）。
6. 帳號只能修改、不能刪除（BR-6）；一經設定，保母即永遠滿足 O2「已設定收款帳號」前置條件。
7. 修改前不要求重新驗證身分（MVP），以「改後立即發不可關閉通知」作為盜改偵測（BR-10、CQ-8）。

### 4.2 未設定時報價（引用）

保母尚未設定收款帳號就報價 → O2 前置條件不符，422 `PAYOUT_ACCOUNT_REQUIRED`（baseline §3.2 O2、§3.7、CQ-63）。檢查與驗收由 PRD-006 承擔；本卡只提供「是否已設定」的查詢給 SD-ORDER（BR-9）。

### 4.3 提供快照（對外 Service）

SD-ORDER 建立 CHARGE payment（PRD-006 O2、PRD-023 補款）時呼叫 SD-SUPPLY「取得帳號以快照」：單次讀取同一筆紀錄的四個欄位（同一版本，不得分次讀取而組出新銀行代碼配舊帳號），不取鎖。與保母同時修改帳號時，快照為修改前或修改後的完整四欄之一，兩者皆合法（BR-12）。

## 5. 狀態轉移

無（帳號沒有狀態機）。

## 6. 業務規則

| # | 規則 | 出處 |
|---|------|------|
| BR-1 | 欄位皆必填：銀行代碼 = 3 位數字（`^[0-9]{3}$`）；分行 = 去除前後空白後 1–30 字；帳號 = 移除所有空白與「-」後 10–16 位數字（`^[0-9]{10,16}$`）；戶名 = 去除前後空白後 1–50 字。前端與後端皆先正規化再驗證，儲存正規化後的值 | 沿用原 PRD-007（A.2 欄位）；格式 CQ-1；正規化為使用者決定 2026-11-21（審查第 1 輪 #9） |
| BR-2 | 只有該保母本人可讀寫自己的即時收款帳號；GET 未設定時回 200 `{ "configured": false }` | baseline §1.2；回應格式為使用者決定 2026-11-21（審查第 1 輪 #1） |
| BR-3 | 修改只影響之後建立的 CHARGE payment；既有 payment 的快照不變 | baseline §1.2、§3.3、CQ-23 |
| BR-4 | 帳號以 AES-256 加密存放；金鑰與業務資料隔離存放，不得有程式內預設值，未設定金鑰時應用程式啟動失敗（金鑰隔離與啟動驗證屬 SD-SUPPLY / 部署驗證項，本卡 AC 只驗儲存值非明文）；payment 快照（PRD-007 BR-2）採同一金鑰管理方式 | NFR-03「敏感個資加密」；baseline §3.3、CQ-23、CQ-72 |
| BR-5 | 訂閱逾期 / 停權時仍可修改收款帳號（§2.2 鎖定範圍只列方案 / 問卷 / 公開檔案設定；BR §5.7.2 鎖定時保留「我的」頁） | baseline §2.2、BR §5.7.2 |
| BR-6 | 收款帳號只能修改，不能刪除（避免已報價待補款時無帳號可快照）；不提供刪除端點，呼叫 DELETE → 405 `METHOD_NOT_ALLOWED`（全域錯誤格式）。帳號註銷依 PRD-000 流程處理，不受本規則限制 | CQ-3；審查第 1 輪 #7、#11 |
| BR-7 | 同一保母多裝置同時修改不做併發保護，最後寫入者為準 | doc-conventions（不處理同一使用者多裝置自我併發） |

| BR-9 | 未設定收款帳號的保母不能報價：O2 前置條件「已設定收款帳號」，不符回 422 `PAYOUT_ACCOUNT_REQUIRED`；檢查在 PRD-006 的 O2，本卡不重複定義 | baseline §3.2 O2、§3.7、CQ-63；CQ-2 |
| BR-10 | 修改收款帳號前不要求重新驗證身分（MVP）；改後立即發 BR-8 的不可關閉通知；重新驗證列入後續強化 | baseline CQ-75；本卡 CQ-8（使用者 2026-11-21） |
| BR-11 | 首次設定（由未設定到已設定）寫稽核紀錄（變更前為空）並發「收款帳號已設定」通知 | 本卡 CQ-6（使用者 2026-11-21） |
| BR-12 | 對 SD-ORDER 的「取得帳號以快照」單次讀取同一筆紀錄的四個欄位，不取鎖；與保母修改同時發生時，快照為修改前或修改後的完整四欄之一 | baseline §3.3；審查第 1 輪 #10 |

## 8. 驗收標準（AC）

### 子模組 1：收款帳號設定

- [ ] **AC-1.1 (首次設定)**：Given 保母尚未設定收款帳號，When 呼叫 GET，Then 200 且 body 為 `{ "configured": false }`，畫面顯示「尚未設定收款帳號」；When 填入銀行代碼「812」、分行「台北分行」、帳號「12345678901」、戶名「王小明」並送出，Then 200，重新讀取回傳 `configured: true` 與相同四個值；新增 1 筆稽核紀錄（變更前為空、變更後「812 / …78901」）；保母收到「收款帳號已設定」站內通知 1 則並排入 Email 1 封；Given 該保母仍未設定帳號時對 PENDING 訂單報價，Then 422 `PAYOUT_ACCOUNT_REQUIRED`、訂單仍 `PENDING`（PRD-006 驗收，本卡僅確認碼名一致），設定完成後同一報價以新的 `Idempotency-Key` 重新送出可成功（前端每次按送出產生新 key；同 key 重送會回放先前的 422，baseline §3.6 冪等）。對應：BR-1、BR-2、BR-8、BR-9、BR-11、EX-10、EX-13
- [ ] **AC-1.2 (欄位驗證與正規化)**：When 銀行代碼「81」或「8123」、分行空白或 31 字、帳號 9 位或 17 位或含非數字、戶名空白或 51 字任一，Then 400 `VALIDATION_FAILED`，已存帳號不變；When 銀行代碼「812」、分行 30 字、帳號 10 位與 16 位、戶名 50 字，Then 200；When 帳號輸入「1234-5678 901」、分行「 台北分行 」，Then 200，重新讀取帳號為「12345678901」、分行為「台北分行」；When 已存帳號為「12345678901」時送出「123-4567-8901」（其餘三欄相同），Then 200 且不新增稽核、不發通知。對應：BR-1、BR-8、EX-4、EX-7
- [ ] **AC-1.3 (權限)**：When 以 OWNER 角色 token 讀或寫收款帳號，Then 403 `ROLE_MISMATCH`；When ADMIN 呼叫，Then 403 `ROLE_MISMATCH`；When 未登入，Then 401 `UNAUTHENTICATED`；Given token 為 SITTER 但保母 profile 不存在，When 讀或寫，Then 404 `NOT_FOUND`，且資料庫未新增保母 profile。對應：BR-2、EX-1、EX-2、EX-12
- [ ] **AC-1.4 (修改只影響新款項)**：Given 訂單 A 的 INITIAL payment `UNPAID` 快照帳號 X，When 保母把帳號改為 Y，Then A 的付款頁仍顯示 X（PRD-007 AC-1.1）；When 之後保母對訂單 B 報價，Then B 的 INITIAL payment 快照為 Y 的四個欄位（銀行代碼、分行、帳號、戶名皆來自 Y）。對應：BR-3、BR-12
- [ ] **AC-1.5 (加密與稽核)**：When 保母把帳號由 X（812 / 12345678901）改為 Y（812 / 98765478901），Then 資料庫中帳號欄位的儲存值不等於明文「98765478901」；新增 1 筆稽核紀錄（操作者 = 該保母、時間、變動欄位「帳號」、變更前後「812 / …78901」→「812 / …78901」），不含完整帳號與戶名；When 只把銀行代碼由「812」改為「700」，Then 新增 1 筆稽核紀錄，變動欄位「銀行代碼」、前後「812 / …78901」→「700 / …78901」；以相同值重送不新增稽核紀錄。對應：BR-4、BR-8、EX-7
- [ ] **AC-1.6 (變更通知)**：Given 保母已在 PRD-014 關閉「訂單事務」等可關閉類別的 Email，When 保母修改帳號成功（任一欄位變動），Then 保母收到「收款帳號已變更」站內通知 1 則並排入 Email 1 封（不可關閉類別），內容含變動欄位名稱與前後「銀行代碼 + 帳號後五碼」（例「…78901」），不出現完整帳號與戶名；以相同值重送不發通知；Resend 失敗時修改仍為 200 且站內通知存在；修改前畫面不要求輸入密碼或重新登入。對應：BR-4、BR-8、BR-10、EX-9
- [ ] **AC-1.7 (訂閱鎖定不擋)**：Given 保母訂閱已逾期鎖定，When 修改收款帳號，Then 200。對應：BR-5、EX-6
- [ ] **AC-1.8 (不可刪除)**：Given 已設定帳號，Then 頁面無刪除按鈕；When 呼叫 DELETE，Then 405 且錯誤碼 `METHOD_NOT_ALLOWED`（全域錯誤格式），帳號仍在。對應：BR-6、EX-11

## 9. 影響範圍
