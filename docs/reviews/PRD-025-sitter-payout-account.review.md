# 審查：PRD-025（第 1 輪，2026-11-21）

結論：需釐清

範圍：`docs/sa/fr/PRD-025-sitter-payout-account.md`（In Review，1 子模組 8 AC）。基準：`docs/sa/00-DOMAIN-BASELINE.md` 第 2 版 §1.2、§2.2、§3.2 O2、§3.3、§3.7；`docs/sa/nfr/03-SECURITY.md`；抽樣 `reports/rereview/00-sample-SD-007.md` #1、#8、#11。

## 抽樣缺陷回顧

| 抽樣 # / 模式 | 結果 |
|--------------|------|
| #11 帳號可隨時改、無快照、盜改風險 | 快照在 PRD-007；本卡加了變更通知與稽核。但通知 / 稽核只呈現帳號後五碼，「只改銀行代碼」或「後五碼相同的另一帳號」無法被察覺（#2） |
| #1 加密金鑰有寫死預設值 | 屬 SD / 部署，但本卡 BR-4 只寫「加密存放」，沒引用 NFR-03「金鑰與業務資料隔離」，AC-1.5 只驗「不等於明文」，寫死金鑰也能通過（#4） |
| #8 找不到 profile 時自建 | 本卡未定義 SITTER 角色但無保母 profile 時的行為（#8） |
| P1–P2 | AC 可觀察；EX-11 405 沒有錯誤碼（#7） |
| P5 竄改 | 只有事後通知；是否需要變更前重新驗證身分未定（CQ-8） |

## 問題清單

| # | 嚴重度 | 位置 | 問題 | 建議修正 |
|---|--------|------|------|---------|
| 1 | 重要 | §4.1、AC-1.1 | 「尚未設定」的 API 回應未定義（404 `NOT_FOUND`？200 + 空值？），AC-1.1 只斷言畫面文案。前後端會各自猜 | 定義 GET 未設定 → 200 `{ "configured": false }`（不是錯誤狀態）；AC-1.1 補 API 斷言 |
| 2 | 重要 | BR-8、§4.1-3、AC-1.5、AC-1.6 | 通知與稽核只記帳號後五碼（CQ-4 已決）。只改銀行代碼、或改成後五碼相同的另一帳號時，稽核前後值相同、通知看不出差異，防盜改目的落空；稽核「值有變動」的判斷範圍（四欄任一？只看帳號？）也沒寫 | 「值有變動」定義為四欄任一不同；呈現方式擴充需使用者決定（CQ-5） |
| 3 | 重要 | BR-8、AC-1.6；PRD-014 §C | PRD-014 允許使用者按類別關閉 Email，但「涉及帳號安全」的通知須強制開啟。本卡 AC-1.6 假設 Email 一定排入，沒說是否受偏好影響 | 依 CQ-7 寫入 BR-8；建議歸「帳號安全」強制開啟 |
| 4 | 重要 | BR-4、AC-1.5 | 未引用 NFR-03（AES-256、金鑰與業務資料隔離存放）。AC-1.5 只驗「儲存值 ≠ 明文」，抽樣 #1 那種「金鑰寫死在 repo 預設值」照樣通過 | BR-4 出處補 NFR-03 並寫「演算法 AES-256；金鑰不得有程式內預設值，未設定時應用程式啟動失敗」；後半屬 SD / 部署驗證，AC-1.5 可維持，於 SD-SUPPLY 補驗證項 |
| 5 | 重要 | §4.1-3、BR-8 | 首次設定（由無到有）是否寫稽核、是否發「收款帳號已變更」通知未定義（BR-8 寫「每次修改成功」，§4.1-3 寫成每次送出都做） | 依 CQ-6 寫明；AC-1.1 補對應斷言 |
| 6 | 建議 | 表頭「歸屬 SD」、「相依 PRD」 | 「§0 涵蓋 PRD 欄尚未列入本卡，待同步」已過時：`docs/sd/00-SD-PLAN.md` §0 SD-SUPPLY 已列 PRD-025。相依「PRD-016（補款 payment 建立）」實際在 PRD-023 | 刪除過時註記；PRD-016 改 PRD-023 |
| 7 | 建議 | EX-11、AC-1.8 | 405 沒有錯誤碼與回應 body；若實作用框架預設 405，回應格式不符 SD-GLOBAL-SPEC 統一錯誤格式 | 寫明 405 `METHOD_NOT_ALLOWED`（全域錯誤格式），或改為「無刪除端點，不定義回應」並刪除 AC-1.8 的 API 斷言、只保留「無刪除按鈕」 |
| 8 | 建議 | §3 | token 為 SITTER 但保母 profile 尚未建立（或已被停用）時的行為未定義；抽樣 #8 的現況是自動建一份 profile | 補一列：無保母 profile → 404 `NOT_FOUND`，不自動建立 profile |
| 9 | 建議 | BR-1 | 使用者常貼上含空白或「-」的帳號；未定義是否在驗證前正規化。分行 / 戶名去空白後儲存的是去空白值還是原值也沒寫 | 前端與後端皆先移除帳號中的空白與「-」再驗證；分行、戶名儲存去除前後空白後的值 |
| 10 | 建議 | §9 對外介面 | 跨角色併發：飼主同意變更（PRD-023 建補款 payment 快照）與保母同時修改帳號。兩種結果都合法，但快照必須是同一版本的四個欄位（不能新銀行代碼配舊帳號） | 對外 Service「取得帳號以快照」補「單次讀取同一筆紀錄的四欄」；不需鎖 |
| 11 | 建議 | BR-6；NFR-08 | 「不能刪除」與 NFR-08 帳號註銷 / 被遺忘權的關係未說明 | BR-6 補「帳號註銷依 PRD-000 流程處理，不受本規則限制」 |
